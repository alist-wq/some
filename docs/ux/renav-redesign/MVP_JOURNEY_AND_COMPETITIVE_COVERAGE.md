## Journey and transition inventory

Each row specifies the entry/goal; main path; failure/interruption and cancellation/recovery; feedback and exit. All rows require paired EN/UK labels, role/action semantics, 48 dp minimum targets, logical focus, Back destination, 150/200% text reflow, light/dark contrast and no color-only status. Those requirements are **design acceptance criteria**, not completed TalkBack results.

| ID | Entry / goal and happy path | Error, interruption, cancel/recovery, feedback and exit |

### Prototype reconciliation and missing design work

The original 17 named states covered the nominal map/search/manual/preview/waiting-guidance path and incident entry, but **did not** separate permission, empty search, route failure, pause, background, departure, recovery, process restart, deletion confirmation or save failure. All ten were **MISSING in the original board**. The extended 27-state board adds these ten design-only states; each moves to **PARTIAL**, not automatically COVERED, until its real transition and exception paths are designed. This is wider *state coverage*, not 27 complete production screen specifications. Additional **PARTIAL** branches that still need owner design decisions before implementation: Android permission denial/permanent denial/settings return; preparation interrupted/no-network/invalid-package details under one plain-language Repair pattern; search loading/index-unavailable/IME; route calculating/replacement; ambiguity versus FreeSpace wording; live eligible-progress vs waiting guidance; arrival pending; incident empty list/save-delete error/expired context. No additional product functionality is authorized by listing these branches.

The board links some states for illustration; it is **not a transition oracle**. Actual transitions must follow existing service/reducer contracts, not button clicks or static text. In particular `recovering` cannot self-promote to active progress, tapping “Continue to Android settings” cannot grant permission, and a static incident Save/Delete action cannot represent filesystem success. Production acceptance must test those branches using the real current build.

## P0 interaction-contract closure addendum — owner principles applied

This addendum is design-only. It resolves what each P0 state *should say and do*, not whether production Android currently performs it. The original 27-state assessment and competitive benchmark above remain historical design inputs. The prototype now has 35 selectable states: eight additions are `permissionDenied`, `partialOffline`, `offlineNetwork`, `destinationRetained`, `routeCalculating`, `active`, `freeSpace` and `arrivalPending`. All are sample conditions, not a second navigation engine.

| P0 decision | Resolved design rule | Design classification / runtime boundary |
| --- | --- | --- |
| Contextual permission | Request live location only in context. Denial does not block a verified offline map; show why live progress is waiting and offer permission review. Return from the OS permission surface must re-evaluate the actual grant; tapping the rationale never grants it. Background access is explained only for explicitly active navigation. | COVERED in `permissions`/`permissionDenied`/`unavailable`; actual OS dialog, permanent denial and Settings-return visuals UNVERIFIED. |
| Offline repair without unnecessary blocking | Treat map, routing and index verification independently. `partialOffline` may show only a **verified** map while Search/Start remain disabled; `repair` covers unusable packages; `offlineNetwork` offers retry and, only if a verified map exists, Explore map. Never label all packages READY until the approved verifier does. | COVERED design contract; real package combinations and interrupted preparation remain existing RB-02/RB-05.2 runtime acceptance, not new claims. |
| Destination retention and route entry | Selection remains valid through no-origin, picker Cancel, route calculation Cancel/FAIL and preview Back. `destinationRetained` is the landing state; replacement occurs only on an explicit new result. Manual confirmation enters `routeCalculating`, not an instant verified preview. | COVERED design contract; no route is active until verified preview + user Start. |
| Distinct guidance availability | `paused` means session-held progress/arrival frozen, while position reliability remains independent. `progressHold` means route ambiguity with trustworthy position; `freeSpace` means no supported route association; `departure` means off-route. `lost` means no eligible current position. Only `paused` exposes Resume, which goes to `recovering` and waits for fresh evidence. | COVERED design contract; no user control forces an ambiguous route match or restores progress. |
| Source/provenance and uncertainty | Manual start remains “chosen on the map”, LOW and manual-start ±100 m in the sample route screens. The ±100 m label describes the chosen origin only. An estimated **current** position must show uncertainty from its own eligible estimate, not inherit the manual-start number. | COVERED sample copy; production values and source display remain service-owned. |
| Arrival | `arrivalPending` is not a success state. Only the existing arrival eligibility contract may transition to `arrival`; manual origin, LOW/LOST, stale, discontinuous, correlated or over-uncertain evidence cannot do so. No prototype button leads to arrival. | COVERED design contract; real Android/field arrival acceptance still open. |

### P0 transition and cancellation matrix

`USER` denotes an explicit control; `SYSTEM` denotes an OS, package, route or service outcome. The static workbench selector can display SYSTEM outcomes, but those must not be user-triggerable shortcuts in production. When multiple conditions coexist, genuine position loss takes precedence over a route-only ambiguity label; pause freezes route progress regardless of position status. A service-owned position category can continue independently during pause/background and must not be promoted by those lifecycle events.

| From / entry | Trigger | To / exit | Cancellation, recovery and invariant |
| --- | --- | --- | --- |
| `ready` or `unavailable` | USER asks for live location | `permissions` | Search/explore remains available when offline packages are verified. |
| `permissions` | OS denies or user declines | `permissionDenied`/`unavailable` | No false grant; no live progress. USER may review permission again or continue map/search. |
| `permissions`/`permissionDenied` | SYSTEM returns from dialog/Settings | Re-evaluate readiness and position, then `ready`/`unavailable` | Never infer success from the Settings trip alone. |
| `preparing` | SYSTEM verifies map only | `partialOffline` | Map exploration allowed; Search/Start disabled. |
| `preparing` | SYSTEM network interruption | `offlineNetwork` | Retry is explicit; verified active packages remain usable. |
| `preparing`/`repair`/`offlineNetwork` | SYSTEM verifies all required packages | `ready` | Only verifier result may show READY; retry button alone cannot. |
| `repair`/`offlineNetwork` | USER retries | `preparing` | No premature READY. If no verified map exists, do not offer Explore. |
| `search` | USER selects new result | `needsOrigin` or eligible-origin route entry | New result alone changes destination; Cancel returns old destination if one existed. |
| `needsOrigin` | USER cancels | `destinationRetained` | No route starts; selected destination remains. |
| `manual` | USER cancels | `needsOrigin` | Same destination; no manual origin committed. |
| `manual` | USER confirms | `routeCalculating` | Origin marked MANUAL_START/LOW and not treated as measured position. |
| `routeCalculating` | USER cancels / SYSTEM fails | `destinationRetained` / `routeError` | Candidate route discarded; valid destination remains. |
| `routeCalculating` | SYSTEM verifies route | `preview` | No user action can bypass verification. |
| `routeError` | USER retries / changes origin / cancels | `routeCalculating` / `needsOrigin` / `destinationRetained` | Never start active guidance from error. |
| `preview` | USER Back / Start | `destinationRetained` / `guidance` | Back clears candidate, not destination; Start owns a valid session but may wait for reliable position. |
| `guidance`/`recovering` | SYSTEM admits fresh position and supported route association | `active` | No progress or maneuver before eligibility; direct GNSS-trust remains ordinary production default. |
| `active` | USER Pause | `paused` | Freeze progress/arrival; retain route/destination and independent position category. |
| `paused` | USER Resume | `recovering` | Await *new* eligible observation; no instant progress restoration. |
| `active`/`guidance` | SYSTEM background transition with authorized foreground service | `background` | On return, reconcile service truth; never blindly show former `active` state. |
| `active` | SYSTEM ambiguous match / FreeSpace / departure | `progressHold` / `freeSpace` / `departure` | Position may remain trustworthy; progress and arrival held, route/destination visible. |
| Any active route | SYSTEM position becomes LOW/LOST/unavailable | `degraded` / `lost` | Unavailable hides precise current-position marker and progress-dependent directions; route remains. |
| Hold, departure, degradation or loss | SYSTEM fresh eligible recovery | `recovering` then `active` only if association also supported | No user Resume on route-only holds, no forced snap, no confidence uplift from route geometry. |
| `active` near destination | SYSTEM proximity but arrival not yet eligible | `arrivalPending` | No “reached” claim; route continues. |
| `arrivalPending` | SYSTEM satisfies definitive arrival gate | `arrival` | Manual/LOW/LOST/stale/over-uncertain evidence cannot trigger it. |
| Any route state | USER Stop or route replacement | `ready`/`destinationRetained` or new generation | Stop invalidates old progress, retains valid destination where permitted; old callback cannot revive guidance. |
| Any route state | SYSTEM process death/recreation | `restart` | No stale position confidence, progress or arrival restored; offline packages remain separately verified. |
